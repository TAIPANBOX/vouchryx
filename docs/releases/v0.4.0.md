# vouchryx 0.4.0

An agent can now hold a credential of its own, and an operator can stop an agent
in one call and keep it stopped across a restart. The release also refuses a token
exchange whose actor token has been revoked, which it used to accept. That last
change is breaking for one kind of caller, so read Breaking and Migration before
upgrading.

## Breaking

- **A token exchange is refused when its actor token has been revoked.** The
  actor token's `jti` is checked against the revocation list, and so is its
  subject: a subject revoked at or after the token was issued refuses it. The
  answer is `400 invalid_grant` with no token. Before, an unexpired credential of
  a revoked agent could be exchanged for a fresh delegation.
- **An actor token with no `iat` is refused while a subject revocation covers its
  subject.** Such a token is checked as issued at the epoch, which every subject
  revocation covers. Before, it was accepted.

## Migration

- **For the first change**, there is no setting to change. A caller whose actor
  token is refused now gets `invalid_grant`. The operator log and the
  `delegation_denied` event name the reason, `actor_revoked`, and the event is
  filed under the actor. A revocation with `VOUCHRYX_REVOCATIONS_PATH` set keeps
  holding across a restart, so the refusal holds with it until the entry expires.
- **For the second change**, the refusal ends when the revocation entry expires,
  or when the identity provider's token carries an `iat` claim.
- Everything new is optional. A deployment that sets neither `VOUCHRYX_AGENTS` nor
  `VOUCHRYX_WORKLOAD_ISSUERS` keeps every behaviour above, except the two breaking
  changes.

## Security

- **A revoked agent could be issued a new delegation.** The actor token of an
  exchange was not checked against the revocation list, so a credential issued
  before the revocation could outlive it as the actor of a fresh delegation. The
  actor is now checked the way the subject already was.
- **A revocation alone did not stop an agent.** It covers the tokens issued before
  its moment, not the ones issued after, so a stopped agent could be issued new
  delegations. A ban closes that: it refuses every grant that would issue anything
  naming the agent, until it is lifted, and it survives a restart when
  `VOUCHRYX_REVOCATIONS_PATH` is set.

## Added

- **An agent's own credential.** `grant_type=client_credentials` (RFC 6749 section
  4.4) issues an agent a five-minute access token bound to the key it proves with
  DPoP (RFC 9449). An agent authenticates with an enrolment key, held here only as
  its SHA-256 digest, or with the projected service-account token of a cluster
  whose issuer is listed in `VOUCHRYX_WORKLOAD_ISSUERS`. The grant is closed until
  `VOUCHRYX_AGENTS` enrols at least one agent. The token is an `at+jwt`, carries
  the agent's `unit` and `org`, and names the agent as `sub` and `client_id`. It
  is not refreshable.
- **Stopping and restarting an agent.** `POST /v1/revoke` with `"ban": true` on a
  subject bans it. `POST /v1/revoke/lift` ends the ban, and never un-revokes what
  the agent held when it was banned. A ban refuses the agent's own credential, a
  delegation to or from it, and a Cross App Access redemption naming it.
- **Records.** An agent's credential is a `delegation_issued` event with
  `grant: "client_credentials"`, filed under the agent. A ban is a
  `delegation_revoked` event with `ban: true`. A lift writes no event, because
  no event type means "a ban ended"; its line in the store and its log line are
  written every time.

## Changed

- **`VOUCHRYX_TRUSTED_ISSUERS` is optional when `VOUCHRYX_AGENTS` is set**, so a
  service for agents alone needs no human identity provider.
- **Every path that signs asks the ban list first.** A new continuous integration
  gate, `scripts/every-issuance-checks-the-ban.sh`, fails when a signing path does
  not, and has its own cases in `scripts/gates-have-teeth.sh`.
- **Documentation.** The surface table and "Walking the loop" name the lift route
  and the endpoint count, and the README has a section on the agent credential.
- **agent-stack-go is still pinned at v1.3.0.** No new dependency.

## Upgrade notes

- The image tag moves from `v0.3.0` to `v0.4.0`. The new variables, `VOUCHRYX_AGENTS`
  and `VOUCHRYX_WORKLOAD_ISSUERS`, are optional and unset means today's behaviour.
- The new route, `POST /v1/revoke/lift`, answers only for a subject that is banned.
- A ban without `VOUCHRYX_REVOCATIONS_PATH` is forgotten by a restart, like every
  revocation there; the answer says so with `"durable": false`.

## Not proven

- No real cluster has presented a workload token. The tests mint tokens in the
  shape a kubelet writes; no real issuer's key set has been configured.
- No enforcement point verifies an agent token yet. This service accepts one only
  as an actor token, until the doors that enforce delegations verify it.
- The `at+jwt` header is signed by a local copy of agent-stack-go's signer, because
  the library writes `typ: JWT` and takes no header. Every token is checked by the
  library's own verifier in the tests.
- An enrolment key is readable by the agent process that holds it. A workload
  token avoids a static secret, but it is just as readable inside its pod.
- A token exchange whose subject token carries no `cnf.jkt` accepts any presenter's
  valid DPoP proof. Agent tokens are always bound, so the new agent path is not
  affected. Binding or refusing unbound subject tokens is planned for a later release.
- The ban table's cap of 10,000 entries is not exercised by a test, and the new
  parsers have table cases but no fuzzing.
- The container image for this tag and the release workflow run on it are checked
  when that run has finished.
