# vouchryx 0.5.0

A token exchange no longer accepts a subject token that carries no key, unless the
operator marks its issuer as one that sends such tokens. The release also adds a
signing mode in which the working key is held by Keyryx's custody client and certified
by Keyryx, and is never read from a file. The first change is breaking for deployments
whose identity provider sends keyless tokens, so read Breaking and Migration before
upgrading.

## Breaking

- **A subject token with no `cnf.jkt` is refused unless its issuer is marked.** The
  exchange answers `400 invalid_grant` with no token, and the reason `subject_unbound`
  goes to the operator's log. Before, anyone holding a captured copy of such a token and
  a valid DPoP proof of their own could exchange it.

## Migration

- For each `VOUCHRYX_TRUSTED_ISSUERS` line whose identity provider sends tokens with no
  key (typical OIDC access tokens), append `|unbound`, so the line reads
  `iss|aud|jwks-path|unbound`. Lines for identity providers that bind their tokens need
  nothing, and lines with three fields still parse.
- A fourth field other than `unbound` refuses the start, and so does the marker on
  `VOUCHRYX_WORKLOAD_ISSUERS`, since a workload token is never a subject token.
- An exchange whose subject token is bound to the presenter's key is unchanged. An
  exchange of an unbound subject from a marked issuer records `subject_unbound: true` on
  `delegation_issued`.

## Security

- **A captured identity-provider token without a key could be exchanged by any caller
  holding a proof.** The holder check that binds an exchange to the presenter ran only
  for tokens that carry a key. An unbound subject token is now refused unless its issuer
  is marked, so the refusal no longer depends on what the token says about itself.
- **The signing key can be held outside any file this service reads.** With
  `VOUCHRYX_SIGNER=keyryx` the working key is generated in memory, held by the custody
  client, and certified by Keyryx for a limited time. Every token is signed with that key
  and with no other, and a token request is refused once the certification has run out.

## Added

- `VOUCHRYX_SIGNER=keyryx`, which needs `VOUCHRYX_KEYRYX_URL`,
  `VOUCHRYX_KEYRYX_CONSUMER`, and exactly one of `VOUCHRYX_KEYRYX_SOCKET` or
  `VOUCHRYX_KEYRYX_CREDENTIAL_FILE`. The service refuses to start if any of them is
  missing or if both of the last two are set.
- In keyryx mode the working key is renewed at half the life of its certification. The
  signer uses a key only once the set this service serves holds it, so a token never
  arrives before a verifier can check it, and the set is refreshed every ten seconds.
- In keyryx mode `GET /healthz` answers `503` with the reason until a working key is
  certified, so it reads as readiness.
- During a migration, `VOUCHRYX_SIGNING_KEY` may be set beside keyryx mode. Its public
  half is published next to Keyryx's key, and it never signs. The file key is never a
  fallback for the working key.

## Changed

- Every token is signed through one seam, `internal/signer`, and a gate fails any other
  signing call in this repository.
- agent-stack-go is pinned at a pseudo-version of the merged keyclient commit
  (`v1.3.1-0.20261018142823-b1f430dea8fd`), not at v1.3.0. The library keeps custody, the
  renewal and the key-set cache, so this service carries none of them.
  `delegation.SignES256` is no longer called.

## Upgrade notes

- The image tag moves from `v0.4.0` to `v0.5.0`.
- With no setting, nothing changes except the unbound-subject rule above. Without the
  Migration step, a deployment whose identity provider sends keyless tokens has its
  exchanges refused.
- The new variables are optional, and only keyryx mode uses them.

## Not proven

- This service does not check Keyryx's root signature on a statement. keyclient checks
  the statement's claims against what it asked for and trusts the channel to custody. A
  socket or a bearer credential is that channel. Pinning a root and verifying each
  statement against it is not built.
- Renewal happens at half the statement's life, which is every 36 hours for a 72-hour
  statement, not the daily cadence in the wave decision.
- The overlap between the old and the next key is Keyryx's to keep. The tests use a
  fake custody, and one live run against a real keyryx binary found a start-up race that
  the served-set check above now closes.
- An unbound actor credential on a first hop is still accepted, and the result is bound
  to the presenter's own key. Only the subject token is covered by the marker.
- A first-hop refusal for an unmarked issuer reaches the operator's log, not the event
  stream, because a first hop has no holder to file it under.
- Nothing here has run against a real identity provider. Interoperability with a
  specific provider is not claimed.
- In file mode the signing key is single, so a rotation replaces it at once, with no
  overlap period.
